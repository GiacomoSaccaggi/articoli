ARRAY, MAP, and ROW Columns No Longer Crash — August 2026

Fixing Trino ARRAY/MAP/ROW Types in ConnectorX

August 2026 · Giacomo Saccaggi · Issue #721

The Problem

Trino supports complex column types: ARRAY, MAP, and ROW (structs). When you query a table with these columns through ConnectorX, it crashes:

-- This query crashes ConnectorX:
SELECT name, tags, metadata, address FROM users
-- tags: ARRAY(VARCHAR)
-- metadata: MAP(VARCHAR, VARCHAR)
-- address: ROW(street VARCHAR, city VARCHAR, zip VARCHAR)

Error: "Trino unknown value at position: (0, 1)"

The type system correctly maps ARRAY/MAP/ROW → Varchar (serialize as JSON string). But the parser's Produce<String> implementation only matches Value::String. When Trino returns Value::Array([...]) or Value::Object({...}) in the JSON response, it falls through to the catch-all error arm.

Root Cause

The impl_produce_text macro generates the Produce trait implementation for text-like types. Before the fix, its match statement only handled one case:

match value {
    Value::String(x) => { x.parse()? }  // ← only this worked
    _ => throw!(...)                   // ← everything else crashed
}

But Trino's REST API returns complex types as structured JSON — not as strings. An ARRAY(VARCHAR) column comes back as ["a","b","c"] (a JSON array), not as the string "[\"a\",\"b\",\"c\"]".

The Fix

Add match arms for the remaining JSON value types, serializing them via serde_json::to_string():

match value {
    Value::String(x) => { x.parse()? }
    // NEW: serialize complex JSON values to string
    Value::Array(_) | Value::Object(_) | Value::Number(_) | Value::Bool(_) => {
        serde_json::to_string(value)
            .unwrap_or_else(|_| value.to_string())
            .parse()?
    }
    _ => throw!(...)
}

Result

Complex columns now appear as valid JSON strings in the output DataFrame:

  • tags (ARRAY) → '["rust","python","data"]'
  • metadata (MAP) → '{"team":"platform","role":"eng"}'
  • address (ROW) → '{"street":"123 Main","city":"SF","zip":"94102"}'

Downstream code can then parse these JSON strings as needed with json.loads() or Polars' str.json_decode().

Why .parse()?

The macro is generic over both String and char. For String, "hello".parse::<String>() is identity. For char, complex types (ARRAY/MAP/ROW) are never mapped to Char in the type system — only single-character CHAR(1) columns use it, and those always arrive as Value::String. The .parse() call satisfies the macro's generic constraint without runtime cost for the String case.
