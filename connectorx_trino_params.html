Fixing Trino Connection Parameters in ConnectorX

"The fastest query is the one that doesn't fail because of a missing header."

August 2026 · Giacomo Saccaggi · Issue #927

Context

ConnectorX is a Rust library (2.6k stars) that loads data from databases into DataFrames at maximum speed. It's the engine behind polars.read_database_uri() when you set engine="connectorx". It already supports Trino — you can connect, run queries, get Arrow results, and even use partition_on for parallel execution.

But while exploring the codebase, I found two issues:

Bug 1: verify=false ignored during partition queries

When you use partition_on, ConnectorX runs a SELECT MIN(col), MAX(col) pre-query to determine the partition range. This pre-query creates a separate client that does NOT inherit verify=false from the connection URL — causing TLS certificate errors on self-signed clusters.

Bug 2: Trino protocol parameters silently dropped

The underlying Rust library (prusto) supports session properties, extra credentials, client tags, source identifiers, and more. But ConnectorX never reads these from the connection URL — they are silently ignored. There is no way to set a query timeout, pass S3 credentials to a Hive connector, or tag queries for resource group routing.

What Trino Supports

The Trino REST protocol defines a set of headers that clients can send to configure the session. Every Trino client (JDBC, Python trino://, dbt-trino) supports these. ConnectorX didn't — until now.

URL ParameterTrino HeaderWhat It Does
source=XX-Trino-SourceIdentifies your application in Trino query logs and the web UI
schema=XX-Trino-SchemaSets the default schema — no need to write schema.table everywhere
client_tags=a,bX-Trino-Client-TagsRoutes queries to specific Trino resource groups
client_info=XX-Trino-Client-InfoMetadata visible in system.runtime.queries
trace_token=XX-Trino-Trace-TokenCorrelates queries across distributed tracing systems
session.K=VX-Trino-Session: K=VSession properties: timeouts, join strategies, memory limits
extra_credential.K=VX-Trino-Extra-Credential: K=VCredentials forwarded to Trino connectors (S3 tokens, Hive auth)

The Fix

I extracted a shared build_client_from_url() helper function that parses all supported URL query parameters and configures the prusto ClientBuilder. Both TrinoSource::new (the main query path) and trino_get_partition_range (the partition pre-query) now use this single function — no code duplication.

Key design decisions

  • DRY: One helper, two call sites. The partition bug is fixed by construction — both paths always get the same configuration.
  • Backward compatible: URLs without new parameters work exactly as before.
  • Minimal: No new dependencies. serde_json, url, HashMap are already in scope.
  • Safe: Empty keys (session.=value) are silently ignored. Unknown params pass through harmlessly.

Before

// Only these worked:
"trino://user:pass@host:8080/catalog?verify=false"
// No way to pass session properties, credentials, or tags.
// Partition queries didn't even get verify=false.

After

// Full Trino protocol support:
"trino+https://user:pass@host:443/catalog?
  schema=analytics&
  source=my-etl-pipeline&
  session.query_max_execution_time=10m&
  session.join_distribution_type=PARTITIONED&
  extra_credential.hive.s3.aws-access-key=AKIA...&
  client_tags=team-data,production&
  trace_token=req-abc-123&
  verify=false"

With Polars

import polars as pl

df = pl.read_database_uri(
    "SELECT * FROM events WHERE dt = '2026-08-18'",
    "trino+https://user:pass@trino.corp.com:443/hive?"
    "schema=analytics&"
    "source=etl-pipeline&"
    "session.query_max_execution_time=10m&"
    "extra_credential.hive.s3.aws-access-key=AKIA...&"
    "client_tags=team-data,production",
    engine="connectorx",
    partition_on="event_id",
    partition_num=8,
)
